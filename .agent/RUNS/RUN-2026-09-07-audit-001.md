## Discoveries
1. **The last commits are trustworthy.** No fabricated tests, no
   phantom verification: every re-runnable claim reproduced (see
   above). The firmware side held up equally well (verified in the
   B2B-Firmware repo this same date).
2. **The uploaded recycling spec is only partially implemented** —
   see TASK-025 for the authoritative gap list. Biggest holes: no
   ESP32-CAM anywhere in B2B-Firmware (reader-only firmware), no
   ENTER/capture trigger, no bottle-first flow, no image persistence,
   no leaderboard, no student login, no recycling WS frames.
3. DeepSeek cost-gating (spec §4) is satisfied for the card-first flow
   by construction — classify REQUIRES an event_id created by a tap
   (card→student), so an image can never reach DeepSeek without a
   student. Bottle-first (spec §3 Case B) simply does not exist.
4. `ClassificationService::classifyAndAward` is NOT wrapped in a DB
   transaction (deposit insert and ledger insert are separate). The
   unique(event_id) index does prevent double-award (a concurrent
   loser gets a raw 500, not a graceful duplicate response), but a
   crash between the two writes leaves a deposit with no points, and
   the unique index then blocks the retry forever. Spec §15/§18.
5. The realtime feed broadcasts `tap` and `pairing` frames only.
   classify/redeem create NO frames — recycling stats on dashboards
   update only on reload. (The DB-poll-then-push WS design itself is
   sound and server-authoritative; it just has no recycling channels.)
6. .agent task numbering was renumbered once (disclosed in c582700's
   message): local docs 020→021, 022/023→023/024 because origin/main
   already held a different RUN-020. Both lineages coexist in RUNS/.
7. `rewards` table has only id/name/point_cost/description — no type,
   value, active, or stock columns; no reward_redemptions table (a
   redemption persists only as a points_ledger row with reward_id).
