## Root cause (from the downloaded job log)

One test failed:

```
FAILED Tests\Feature\Api\CardPairingTest >
  arming then pairing a fresh card links it to the student
  expires_at should be ~45 s in the future
Failed asserting that 1788905697 is identical to 1788905698.
  at tests\Feature\Api\CardPairingTest.php:91
```

Mechanism: the endpoint stamps `expires_at = now()+45 s` at T1
(`toIso8601String()` truncates sub-second precision); the test then
RE-computes `now()->addSeconds(45)` at T2 and asserted `assertSame`.
Any second boundary falling between T1 and T2 makes the two truncated
timestamps differ by exactly ±1 s. The Windows runner is slower (37 s
full pyramid vs ~30 s here) so the race landed. Same code passed runs
#80/#81 — a genuine environment-timing flake, NOT a regression of
6388153.

## Fix

`tests/Feature/Api/CardPairingTest.php` — replace the exact-equality
assertion with the repo's own tolerance convention (TapEventTest
already uses `assertEqualsWithDelta` for client timestamps):

```php
$this->assertEqualsWithDelta(
    now()->addSeconds(45)->getTimestamp(),
    $arm->json('expires_at') ? strtotime($arm->json('expires_at')) : 0,
    1,
    'expires_at should be ~45 s in the future'
);
```

±1 s tolerance covers the truncation boundary while still failing
loudly for any real window change (0, 30, 60, already-expired). The
in-code comment documents the mechanism + the CI run ID.

## Traps (durable)

- **Clock-boundary `assertSame` flake family**: any assertion that
  re-computes a `now()`-derived timestamp AFTER the response under
  test was generated can fail with exactly ±1 s when a second
  boundary falls in between (sub-second precision is truncated on
  both the ISO string and `getTimestamp()`). Use
  `assertEqualsWithDelta(..., 1, ...)` — established TapEventTest
  precedent. This is the feature-test sibling of the already-recorded
  e2e WS-timing flake guidance ("flake-suspect first, re-run before
  debugging").
- **The observation gap**: RUN-025 recorded runs #80/#81 green but
  was pushed as 5870b07, whose OWN run #82 failed 3 minutes later —
  a record that says "CI green" is only ever about the commits it
  actually observed; observe the run triggered by the record commit

## Follow-up — run #83 exposed a SECOND flake (same observation round)

Remote run **34285994702** on d10476a: **13/14 jobs green** —
including `Windows smoke` (the CardPairingTest fix above is now
verified on the real windows-latest runner) — but the
`Real-HTTP E2E (serve + curl, via ./run e2e)` job failed ONE check:

```
FAIL Taps now register as PAE_LUNCH — expected ["event_type":"PAE_LUNCH"] in:
{"status":"error","reason":"student_not_pae",
 "message":"Ana is not enrolled in the PAE feeding program"}
```

Root cause (reproduced locally, `scripts/prove_e2e_flake.sh` pattern
— EXPLAIN + 12 reseed simulations): `scripts/e2e.sh` picked the demo
card with `SELECT credential_uid FROM cards LIMIT 1` — **no ORDER
BY**. SQLite serves that from the covering unique index
(`SCAN cards USING COVERING INDEX cards_credential_uid_unique`, per
EXPLAIN QUERY PLAN) → index order → the alphabetically-first RANDOM
`Str::random(12)` UID → the owner is a **per-run dice roll over the
4 demo students**. 12 simulated reseeds drew 4 different owners,
including Ana Martínez (the single `pae_enrolled = false` student) —
exactly the CI failure. When her card is drawn, the relabel-phase
tap correctly hits the TASK-027 PAE gate (422 `student_not_pae`)
and the pre-gate-era check fails. Local runs had simply been lucky
(~1-in-4 odds; ~7 consecutive non-Ana draws before #83).

Fix: one deterministic, PAE-valid, coherent selection —

```sql
SELECT c.credential_uid, c.student_id FROM cards c
JOIN students s ON s.id = c.student_id
WHERE s.pae_enrolled = 1 ORDER BY c.id LIMIT 1
```

— `ORDER BY c.id` makes the pick planner-independent, the
`pae_enrolled` filter satisfies the PAE gate for the relabel tap,
and a SINGLE query also removes a second latent bug: CARD_UID and
STUDENT_ID previously came from two separate unordered LIMIT 1s
that could disagree (the redemption phase spends the points the
CARD_UID owner earns via STUDENT_ID). Proof: 12/12 reseeds now draw
Maria González (pae=1); all downstream e2e checks are name-generic.
