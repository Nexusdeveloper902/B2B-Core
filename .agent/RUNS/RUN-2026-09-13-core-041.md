# RUN-2026-09-13-core-041 — Reader deletion (desk overflow + endpoint)

Owner ask (chat, 2026-09-13): readers can be created/renamed/rotated
from `/admin/readers` but never removed — a decommissioned reader
has no exit path short of SQL.

## Changes (this repo only)
- **`DELETE /api/v1/admin/readers/{reader}`** (admin-only,
  teacher → 403, guest → 401, unknown → 404) in
  `ReaderController::destroy`: the row goes with its tap events +
  recycling deposits + pending captures (explicit child-first
  deletes — same order a DB cascade would apply, deterministic
  where the sqlite foreign_key pragma is off, cf.
  CardUnpairController). Pairing history survives with `reader_id`
  nulled (audit trail); `points_ledger` rows survive with
  `event_id` nulled (the `nullOnDelete` FK — balances keep their
  value); stored capture images follow their rows off disk. A
  `reader_deleted` roster frame (`RosterUpdate::TYPE_READER_DELETED`)
  is written in the same transaction; the old Bearer key 401s with
  the row.
- **Desk**: Save stays out; Rotate + Delete tuck behind a ⋯ button
  in a native `popover` menu (top-layer by construction — never
  clipped by the ledger scroll container; light-dismiss + Esc
  free). JS pins the open popover under its button (fixed
  positioning, no anchor-positioning dependency). Delete runs the
  Datum confirm, then removes the row client-side AND on the live
  `realtime:roster` `reader_deleted` frame (empty-state row
  restored when the last reader goes). Dynamically-added rows
  (post-create) build the same menu.
- **Bilingual**: `api.reader_deleted`, `app.delete_reader` /
  `delete_reader_confirm` / `reader_deleted` /
  `toast_reader_deleted` / `reader_more_actions` (EN+ES).
